# 按种子救援：双 qBittorrent 容器替代全局隧道切换

Status: proposed
Class: architecture

## 背景

ExpressVPN 不提供端口转发，qBittorrent 长期 firewalled——只能主动拨出、无法接听。
swarm 里多数 peer 同样在 NAT 后，两边都只能拨号就永远握不上手。
实测：某种子 51 个做种者**一个都连不上**，卡在 8% 两天不动。

2026-08-19 上线的止血方案是**全局切换**（`~/gluetun/rescue.py`）：
临时把 gluetun 从 ExpressVPN 换成自有 VPS 的 WireGuard（该 VPS 上做了 6881 的 DNAT），
跑完再换回来。效果立竿见影：

| | 切换前 | 切换后 |
|---|---|---|
| 总下载 | 8 KB/s | 1566 KB/s |
| 已连做种者 | 0–1 | 4–7 |

但它有个笨重之处：**切换前必须暂停全部 380 个做种种子**。
因为库里积着约 249 GB 上传欠账（411 个完成种子里七成分享率不到 0.1），
一旦可被连入又不暂停，几小时就能烧穿 VPS 每月 1TB 的配额。

## 提议

跑两个 qBittorrent 容器：

- **主容器**（现有 `qbit-vpn`）：走 ExpressVPN，持有全部种子，正常做种
- **救援容器**（新增）：走 VPS 的 WireGuard，平时空转，只在需要时接活

**关键设计：不搬种子，只借下载。**

```
1. 主容器：把卡住的种子**暂停**（记录与 ab: 标签原地不动）
2. 救援容器：用**完全相同的 save_path** 添加同一个种子，下载
3. 下完：救援容器移除该种子（保留文件）
4. 主容器：恢复 + recheck → 看到 100% → 开始做种
```

## 为什么不直接把种子搬过去

AutoBangumi 改名靠主容器里的 `ab:<bangumi_id>` 标签反查 episode_offset。
种子一旦搬走，标签就丢了——症状是"文件下好了但永远不改名"，
而且**不报错**。这个坑 2026-08-18 刚踩过一次
（见 `implemented/bug-fix/2026-08-18-subscribe-missing-ab-tag.md`）。

上面的"借下载"方案里主容器全程持有种子记录，标签问题根本不出现。

## 收益

- 不必暂停 380 个做种种子，主容器业务不中断
- VPS 只承载被救的那几个种子，配额消耗从"整库敞开"降到"几个 GB"
- 没有全局切换窗口，失败影响面小
- 可被 media-agent 自动化：`stalled-torrent` 检测器 + `rescue_torrent` 动作

## 必须严格的地方

**两个客户端绝不能同时写同一批文件。** 主容器必须确认已暂停，
救援容器才能开始。顺序错了会损坏正在写的分片，而且损坏不会立刻暴露——
要等 recheck 或播放时才发现。动作实现里这一步要有硬校验，
不能只发暂停请求就往下走，得确认状态真的变成 stopped。

## 需要落实的细节

- 救援容器的 WebUI 端口（主容器占 1122，用 1123）
- 两容器都挂 `/Volumes/Backup/webdav/Media` 同路径
- 判定"卡住"的阈值：多久无进展 + 已连做种者数（现成数据：`num_seeds` vs `num_complete`）
- 救援完成后主容器 recheck 的等待与校验
- 与 `vpn-watchdog` 的关系：救援容器独立于主隧道，看门狗只管主容器，
  比全局切换方案简单（后者需要 `.rescue-active` 标记让看门狗避让）

## 现状

全局切换方案已上线可用，作为兜底保留。本提议是它的演进方向，不是替代品——
主容器整条链路出问题（比如 ExpressVPN 服务器 IP 轮换导致隧道全断）时，
全局切换仍是唯一手段。
