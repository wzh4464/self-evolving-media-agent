# 改名为什么总出错：腾空必须先于命名

## 症状的规模

审计日志里 `rename/skipped` **2657 次**，原因**全部**是同一句：

```
目标文件名已存在，避免覆盖
```

不是偶发，是唯一的失败模式。

## 为什么

改名只有一种失败方式：目标名被占。而目标名是 `{标题} SxxExx.ext` ——
一个集位按定义只能有一个文件。所以"被占"永远意味着**同一集有两个文件**，
那是集位归属问题，不是命名问题。

而这两件事被拆成了两条独立规则，按固定的全局顺序执行：

```python
_OP_ORDER = { ..., "rename": 6, ..., "trash": 9 }
```

同一批次里：

1. `rename` 想把 `[Sakurato]…[20].mkv` 改成 `入间同学入魔了！ S04E20.mkv`
   —— 该名字被另一个版本占着 → **跳过**
2. `trash` 把占位的那个清掉 → 名字腾出来
3. 批次结束，赢家仍留在原始发布名上

要等**下一轮**（6 小时后）才可能改名。而「谁先出要谁」**必然**产生重复——
多个字幕组发同一集是常态，不是例外。于是这条路径被反复走了 2657 次。

2026-09-04 用户报"最新的入间同学没改名"：E20 有 Sakurato 和 Nix-Raws 两个版本，
判重留下 Sakurato，但改名在腾空之前跑，连续两轮都跳过，文件在库里躺了 13 小时
无法刮削。

## 逻辑上不出错的办法

不是"再加一次重试"，也不是"改名时顺手删掉占位的"（那等于让命名逻辑做删除决策）。
要的是一条**前置条件保证**：

> 一个集位只能有一个文件。所以：**先解决集位归属（腾空），再命名。**

把 `trash` 排到 `rename` 之前，改名的前置条件就从"碰运气"变成"有保证"：
走到 rename 时，该集位的其它claimant 已经不在了，目标名一定是空的。

```python
"write_nfo": 5,
"trash": 5,        # 腾空
"rename": 6,       # 再命名
```

安全性：三个 trash 来源（`duplicate-episode` / `dead-torrent` /
`extras-in-library`）都不依赖改名先发生。而且 trash 是"移入隔离区 + 记录逆操作"，
不是 `rm`——原先把它排在最后所依据的"破坏性操作放最后"这条直觉，
在这里保护的东西本来就不多，代价却是每次重复都损失一个完整周期。

## 剩下的失败是真的失败

改完之后，`_op_rename` 再撞名就只剩一种解释：**这一轮没能腾空**——
同一集位有两个文件而 `duplicate-episode` 判不出取舍（画质无法比较之类）。
那是需要人介入的真冲突，不该和"排队等改名"长一个样。所以审计信息也改了：

```python
"reason": "集位被占：目标名已被另一个文件占用，且本轮没有腾空",
"occupant": target.name,
"hint": "同一集有多个版本，等 duplicate-episode 判出取舍；"
        "若它也判不了，需要人工介入",
```

## 效果

改动后单轮 `跳过 0 项`，全库 `unrenamed` 归零。

## 更一般的教训

这一整天里改名出过四次错，事后看是同一个形状：

| | 表现 | 实质 |
|---|---|---|
| Re:Zero E58 | AB 按分季集号改名，撞掉真实的第 8 集 | 两个改名者，两套集号口径 |
| E58 来回改名 | 摘 `ab:` 标签拦不住 AB | 用错了所有权开关（是分类不是标签） |
| 新抓的集 6 小时不改名 | 交接后没人接管"60 秒内改名" | 换组件时漏接了它顺带提供的东西 |
| 入间 E20 | 改名永远撞名 | 腾空排在命名之后 |

共同点：**改名从来不是一个孤立动作，它依赖一串前置条件**——集号口径一致、
所有权明确、集位空闲。每次出错都是某个前置条件没有被保证，而只是被假设。
