# 改成「谁先出要谁」，以及旧模型的尺子量新模型

Status: implemented
Class: architecture
Rule: `episode-available`（新）／`source-abandoned`、`incomplete-season`（改）

## 背景

原模型：订阅锁定**一个字幕组**的 feed，靠 `filter` 黑名单挡掉其余。
不会重复，但那个组慢或停更整部番就卡住，换源要人工介入——
本 session 手工换过三次（相反的你和我、二十世纪电气目录、Re:Zero）。

新模型：盯**整个番组页**（不带 subgroupid = 全字幕组），缺哪集就在当时
可得的候选里挑最优的抓。判重不靠"锁定一个源"，靠 sidecar 里的
`seasons[N].have` 集号清单。

判重必须在 media-agent 做：AutoBangumi 的 `filter` 只是文件名黑名单，
表达不了"这集我已经有了"。

## 择源：能看 > 快

"谁先出要谁"有个陷阱：**最先出的经常不是能看的**。
实测尼古喵喵 E08 当天只有 ABEMA 转载版，抓下来 711MB，
ffprobe 一查零字幕轨、纯日语音轨。

所以 `preferences.py` 把判定分成两层：
- **硬门槛**：必须有中文字幕，不满足直接淘汰，多快都没用
- **偏好打分**：无删减 +100 / 简中 +50 / 内封 +20，删减版 −90 / 仅繁中 −30

规则存 `.agents/preferences.json`，每次运行重读，改完立刻生效。
局限要说清楚：这是对**发布标题**的启发式，不是对文件内容的检验。
真正的验证只能等下载完 ffprobe——在带宽不紧张时这个取舍划算。

## 踩坑一：多个目录抢同一个 tmdb_id

grab 上线后连续三天、每 6 小时为《入间同学入魔了！》抓一次 S04E19，共 12 次，
11 次 qBit 返回 409。

根因：库里有三个历史遗留的分季目录（`！` / `！！` / `！！！`），
sidecar 全写着 `tmdb_id=91801` 且都认领 season 4，于是各自以为缺 E19，
轮流去抓。

**为什么三天没被发现**：qBittorrent 靠 infohash 挡住了重复下载，
没有重复文件、没有浪费带宽、审计日志里每条都是 `applied`。
正因为没造成损害，也就没有任何信号——只有去数 `grab_episode` 记录、
看出同一集反复出现才暴露。与几天前演进器不收敛是同一种形态：
**系统在"正常工作"，逐条指标都合格，只有看累积模式才发现它在原地打转。**

修复：宿主判定——多个目录共享 tmdb_id 时只认文件最多的那个，
其余跳过并单独告警一次（新 kind `duplicate_show_dir`），而不是静默忽略。

## 踩坑二：旧模型的尺子量新模型（改了三轮才对）

`source-abandoned` 与 `incomplete-season` 对同一部番给出**相反结论**：

```
[critical] 二十世纪电气目录：订阅源已停更，落后 2 集
[minor]    二十世纪电气目录：缺 1 集（均在 7 天内播出，等发布即可）
```

三轮才修到根上：

1. 加"内容齐全就不报"——朱音落语的误报消了（磁盘 E01-E13 齐全，
   TMDB 全 12 集播完，源慢不构成问题），但冒出三条新的
2. 加"落后的集是否刚播出"——无职转生消了，另两部仍矛盾
3. 找到真正的根因：**在"谁先出要谁"模型下，"订阅锁定的那个源落后"
   本身已不构成问题**。二十世纪电气目录的 E07 桜都没发，但抓取器早从
   别的组拿到了、磁盘上有。此时报"源已停更"就是拿旧模型的尺子量新模型。

改成只算**既落后、又确实缺在磁盘上**的集，两条规则从此用同一把尺子
（都是 `RECENT_DAYS = 7`），不可能再矛盾。

验证：`source-abandoned` 0 条，`incomplete-season` 3 条全部 minor 且标注
"等发布即可"，交集为空。

## 教训

**换模型时，旧模型下成立的判断依据会静默失效。** `source-abandoned`
的前提是"我们依赖某个特定的源"——这个前提在改成先到先得的那一刻就不成立了，
但规则本身不会报错，只会继续用失效的前提得出结论，而且结论看起来很合理
（"源确实落后了"是事实）。

前两轮修复都是在症状上打补丁，第三轮才碰到设计层。
如果第一轮就宣布修好，会留下一个每天报两条矛盾告警的库。
