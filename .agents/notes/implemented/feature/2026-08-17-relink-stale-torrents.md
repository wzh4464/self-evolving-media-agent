# 死链种子修复：大小定位 + 哈希校验

Status: implemented
Class: feature
Rule: `stale-torrent-path`

## 现象

库里有 28 个种子的 `content_path` 指向不存在的文件——文件还在，只是被
文件系统 `mv` 改过名/挪过位，qBittorrent 的记录没跟上。这些种子既做不了种，
也让所有按磁盘归属分组的规则都够不着它们。

最初的判断是"只报不改：重新定位需要确认新旧文件对应关系，不能盲目自动做"。
这个判断**下早了**——对应关系其实是可以机械确定的。

## 决定

两段式：**用文件大小定位，用分片哈希证实。**

1. **定位**：种子记录里存着每个文件的精确字节数。在库中按大小找，
   若恰好只有一个候选，那就是它。体积精确到字节相同而内容不同的概率可以忽略；
   实测 28 个种子全部**零歧义**唯一命中。
2. **重建关联**：`renameFile(hash, 旧相对路径, 新文件名)`。这里 `renameFile`
   不是"改文件名"而是"改种子对文件的期望路径"——目标文件已经存在，
   qBittorrent 只更新自己的映射。
3. **证实**：`recheck` 触发 libtorrent 逐分片校验哈希。
   **校验通过才算真修好** —— 大小匹配只是定位手段，哈希才是证据。
   这一步是整套修复敢于自动执行的依据。

全程走 qBittorrent API，不碰文件系统，符合"所有改动必经 qBittorrent"的约束。

## 两个必须处理的边界

**搜索范围。** 首版只在 content_path 推出的 show 目录里搜，结果 18 个古诺希亚
修好了，10 个 Re Zero 全部落空——因为它们的 `save_path` 指向
`Re Zero kara Hajimeru Isekai Seikatsu/Season 3`，而那个目录早在之前的
标题对齐里被合并掉了。**目录本身都不存在，在原地找当然找不到。**
改为：show 目录还在就只索引它（范围小、更安全）；目录已消失则退化为全库索引。

**跨目录重定位。** 文件搬到别的目录后，光 `renameFile` 不够——它用的是
相对 `save_path` 的路径，跨不出去。必须先 `setLocation` 把 save_path 挪过去
再改名。多个文件分散在不同目录时不敢自动处理（种子内部结构无从还原），
归入 unresolved 只报不改。

## 结果

```
死链种子   28 → 0
种子状态   362 个全部 stalledUP
完整度     362/362 全部 100%（分片哈希校验通过）
```

分两批执行：18 个同目录内改名（批次 20260817T175300），
10 个跨目录重定位（批次 20260817T175611）。两批都可单独回退。

## 放弃的替代方案

- **只报不改，让人处理**：最初的选择。28 个手工核对不现实，而且对应关系
  本来就是可机械确定的——是我低估了大小匹配的判别力。
- **按文件名相似度匹配**：改名前后可能毫无字面关系
  （`GNOSIA - S01E08 [WebRip...]` → `古诺希亚 S01E08.mkv`），不可靠。
- **直接 recheck 让 qBittorrent 自己找**：recheck 只在**当前** save_path
  下按**当前**文件名找，找不到就把进度归零。必须先把关联建对。
- **算完整内容哈希再比对**：几百 GB 的读取量，而 libtorrent 的 recheck
  本来就会做分片校验，重复劳动。

## 风险与缓解

**大小碰撞。** 两个不同文件恰好字节数完全相同时会误配。
缓解：候选数 >1 一律归入 unresolved 不给动作；且最终有 recheck 把关——
配错了哈希校验会失败、进度掉下来，能立刻发现。

**全库索引的开销。** 只在 show 目录消失时才触发，且结果按 key 缓存复用。
