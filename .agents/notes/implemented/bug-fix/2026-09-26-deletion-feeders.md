# 喂给删除的检测器错误（整改第 2 阶段，逐节追加）

**日期**: 2026-09-26
**状态**: implemented / bug-fix
**触发**: 整改第 2 阶段要在执行器里加一道统一的删除关口，而关口只能拦住
"执行那一刻看得出来的"错误；检测器把集号算错、把正片当特典、把合集整个判输，关口看到的
就是一条参数自洽的删除。这份笔记记录喂给删除的几处检测器错误，按提交逐节追加。

## 1. AutoBangumi 的 `episode_offset` 只换算发布名，不叠加到已规范的名字上

**现场**：生产 AB 订阅 id 37，《超超超超超喜欢你的100个女朋友》第三季按绝对集号 25–36 发布，
`episode_offset=-24`。AB 把 `- 25` 换算成第 1 集、改名成 `… S03E01.mkv`。

**错在哪**：`builtin._resolve` 对**每个**没钉 `ma:` 的文件都加这个偏移（`_apply_offset`）。
已经是 `S03E01` 的规范名再减 24，落进 `(3, -23)`；刚下完、还叫 `- 25` 的新版本落进 `(3, 1)`。
后果：

- 同一集的两个文件永远不在同一个判重桶里，重复看不见；
- 新版本的改名撞上「集位被占」，每轮一条跳过；
- `kernel.episode_of_file`（`have` / 抓取 / 订阅健康的集号来源）完全不看偏移，把 `- 25` 算成
  第 25 集——同一个文件在两条链路上是两个答案；
- 原始集号本来就是季内编号时（`S3 - 01`）减出负数，改名规则会提议 `S03E-23`。

**修法**：`naming.apply_episode_offset(raw, ep, offset)`——名字里有显式 `SxxEyy` 就原样返回
（那是换算之后的结果），否则加偏移；结果不是正数返回 None（认不出，交给人）。`_resolve`
与 `episode_of_file(…, episode_offset=)` 共用它；`have_episodes` 从订阅行取偏移传进去。
`Sxx - yy` 这种带季号但不是 `SxxEyy` 的发布名照旧换算（AB 对整条订阅的原始集号都加偏移）。

**影响面**：整改前的只读核实——生产只有 AB id 37 这一条订阅的偏移非 0。`grab._inflight` 只认规范名
（`allow_release_name=False`），不受影响；`subscription._disk_episodes` 对这部番的发布名
从此按季内集号计。

**测试**：`tests/test_episode_offset.py`——规范名与发布名落进同一个桶、判重看得见这对重复；
`episode_of_file` / `have_episodes` 与判重同一口径；换算出负数的是 `unparsable`、不提议改名；
对照组：发布名照旧换算。改前 4 条红、对照组绿。
