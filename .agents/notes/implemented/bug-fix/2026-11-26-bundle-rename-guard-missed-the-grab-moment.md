# 合并发布的改名保护在抓取那一刻没生效：数的是种子的条目，不看盘上有没有文件

**日期**: 2026-11-26
**状态**: implemented / bug-fix
**触发**: 2026-11-26 查另一条告警时发现《学生会也有洞！》S01E08 的限制解除版从 11-22 起一直叫发布名，
`unrenamed-file` 的改名连着 17 轮记 `unknown`。那时生产已经是 v0.5.3——上一篇
（[2026-11-19](2026-11-19-bundle-rename-prefers-uncut.md)）说修好了的就是这件事。

## 现象

```
11-22 06:46:00  grab_episode   [TV版&无修版] 学生会也有洞！ - EP08（两个视频，都钉 ma:S01E08）
11-22 06:46:03  rename applied 【10月】… 08【TV放送版】.mp4 → 学生会也有洞！ S01E08.mp4
11-22 06:46:03  rename skipped 【10月】… 08【限制解除版】.mp4（集位被占）
11-22 12:46:48  trash  applied 学生会也有洞！ S01E08.mp4（bundled_version：作废 TV 那一个文件）
此后每轮        rename unknown 限制解除版 → S01E08：renameFile 409「文件已存在」
```

判重留对了版本，但 TV 版先拿走了集位名；它被作废后条目名还占着，限制解除版永远改不过去。

## 根因

`_pinned_siblings` 数「同一个种子里钉着这一集的视频有几份」时多写了一个 `and not is_phantom(f)`。`is_phantom` 的判据
是「有种子、盘上连 `.!qB` 都没有」，它只对**下完的**文件成立（它自己的 docstring 写着）。刚加进来的种子进度 0，两个
文件一个字节都还没写，都被当成幻影、都不算，计数是 0，保护在它唯一要管的那一刻没生效。一个文件已经有 `.!qB`、
另一个还没开始写（下载头几分钟的常态）时计数是 1，同样不生效。

那个条件是上一版提交前临时加的，想防「下完之后丢了的那一份拖住另一份、让它永远改不了名」。**这个担心不成立**，而且
当时没有验证：实测判重会把丢了的那份作废（`bundled_version` 带 `phantom`：它当不了保留方），同一轮的下一次迭代
另一份就改名。一个没有测试、理由也没核实的条件，换来了它要保护的东西整个失效。

上一版的用例也搭不出这一刻：只有「已下 30%」（两个 `.!qB` 都在）和「已下完」，都是用 `lib.show().torrent(progress=…)`
直接摆出来的中间状态。

## 做法

1. `_pinned_siblings`：删掉 `and not is_phantom(f)`。数的是种子的条目（不下载的条目扫描时已经剔掉），不看盘上有没有
   文件。规则回到一句话：同一个种子里钉着同一集的视频不止一份时谁都不改名，由判重作废到只剩一份。
2. 审计说实话（约束 11）：`_op_rename` 在发 renameFile 之前看一眼同一个种子的条目（`_entry_at`），目标路径已经是
   另一个**已设为不下载**的条目的，就不发请求，记一条写明原因和占用者的 skipped（不以「集位被占」开头，同一轮
   不重试——没有动作会去挪一个不下载的条目）。以前照发、撞 409，新旧两个名字此刻都列在条目里，
   `_rename_landed` 说不清，记成 unknown「也许生效了」，其实一次都没生效；占用索引不把不下载的条目算作声明者，
   所以前面的占用闸门拦不住。健康报告里它仍然看得见（卡住检测、发布名超过 12 小时），只是不再说「也许生效了」。

   只管不下载的条目。还要下载的同种子条目是声明者，占用闸门照旧按「集位被占」拦下、可重试（它自己这一轮可能
   被改走）。第一稿对两种都记不可重试的跳过，PR #6 的 review（Sourcery）问到后一种；核实后一种走不到这里，那个
   分支既走不到也没有测试，删了，补了一个用例守住「还要下载的 → 集位被占 → 腾出来之后改得成」。

## 没做的

- **作废的条目自动让位**（改名前把它改成别的名字）。它要连回退一起改：作废的逆操作按条目序号恢复优先级
  （`_restore_priority`）、`restore_from_trash` 把文件搬回原路径；条目改过名之后两者就对不上了。修好第 1 条之后新的
  合并发布走不到这个现场，不值得为它动回退。走到了就人工两步：`torrents/renameFile` 把作废的条目改回发布名
  （它不下载、盘上没有文件，qBittorrent 只改映射；2026-11-26 生产上对 S01E08 实测），下一轮 `unrenamed-file`
  自己把留下的那份改到集位名。
- **抓取时就挑**：加种那一刻按文件名的偏好分把落选的那份设为不下载，留下的立刻改名。这样不用等、也不白下一份
  TV 版。是功能（新的写路径：审计、逆操作、删除关口都要接），不是这次的修补。

## 代价照旧

合并发布要等「下完之后的那一轮 run」才改名（判重作废落选的 → 同一轮下一次迭代改名），最长晚一个 run 间隔
（生产 6 小时），这段时间刮削器认不出它。单视频种子仍是加种就改。上一篇写的「下完才改名」不够准确。

## 测试

`tests/test_bundle_rename_prefers_uncut.py` 下半部分：
- 走真实的 `grab_episode` 动作加一个两视频的种子（进度 0、盘上什么都没有），随后一次 `cycle` 不改任何名字——这是
  生产上 06:46:03 那一刻；
- 只有一个文件开始下载（各一种）时不改名；
- 从抓取到下完：`loop` 一轮里先 trash 后 rename，集位名归限制解除版，TV 条目留着原名、不下载，再跑一轮没有动作；
- 下完之后被删掉的那一份：`loop` 一轮里判重作废它、另一份改名（上一版那个条件想防的情形，现在有测试守着）；
- 旧现场：一轮一条写明占用者的 skipped，不发 renameFile、没有 unknown；把作废的条目改名之后下一轮自己改完；
- 占着名字的同种子条目还要下载（没下 / 下完各一种）：记的是可重试的「集位被占」，它被改走之后改得成。

变异核对（都只跑这个文件）：改回 v0.5.3 的 `and not is_phantom(f)` 红 4 个；让计数恒为 0 红 8 个；去掉条目重名的
预查红 2 个。全量 1173 个通过。

## 教训

- 搭事故现场要走事故发生时的那个入口（这里是抓取动作），不要直接摆中间状态。
- 往一个保护里加例外之前，先证明例外要防的事会发生；加了就给它写一个去掉它会红的测试。
